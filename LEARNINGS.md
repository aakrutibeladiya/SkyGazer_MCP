# Learnings

Running notes on things worth remembering later. Add an entry whenever something is non-obvious, surprising, or took more than a couple minutes to figure out. Newest at the bottom of each section.

## MCP core concepts (primer, fill in / correct as understanding deepens)

- **Tools** — actions the model can *call* with arguments (like a function call). Use for anything that takes input and does/returns something: "get today's APOD", "search Mars photos for sol 1000".
- **Resources** — data the client can *read*, addressed by URI, usually without arguments (or simple ones). Think "list of files" / "list of valid rovers" — things you'd browse rather than invoke. Resources can be listed and read separately, and clients may cache them.
- **Prompts** — reusable prompt templates the server exposes to the client. Not used in this project (yet).
- **Transport** — how client and server talk. Local servers typically use stdio (spawn a process, talk over stdin/stdout). Remote servers use HTTP/SSE.
- **Schema validation** — tool inputs are declared with a JSON Schema (via Zod in the TS SDK). The client/model sees this schema and it constrains what arguments get sent — get it precise, since it's effectively the tool's API contract.
- **Content types in responses** — a tool result isn't just text; it can be text, image, or embedded resource blocks. NASA's imagery APIs are a natural fit for testing image content blocks specifically.

## NASA API notes

- There are (at least) two separate NASA API families: `api.nasa.gov` (APOD, Mars Rover Photos, NeoWs, EPIC, DONKI — needs an API key) and JPL's **SSD/CNEOS API** (`ssd-api.jpl.nasa.gov` — Close Approach Data, Small-Body Database, Sentry, Fireball, NHATS — no key needed). Different base URLs, different fair-use rules; don't assume one client config covers both.
- SSD API fair-use rule that actually affects code: **no simultaneous requests** — any client for this API must serialize calls (no `Promise.all` fan-out), not just rate-limit them. Its "no embedding in a website" / CORS rule doesn't apply to a server-side MCP server — that's a browser-only restriction.
- SSD API responses include a `version` field specifically because formats can change without notice — worth checking it against an expected value and warning on mismatch rather than assuming the shape.
- **SBDB "not found" is a soft error, not an HTTP error** — `sbdb.api?sstr=<unknown>` returns HTTP 200 with `{code:"200", message:"specified object was not found", moreInfo}`, no `object` key. Genuine malformed requests (missing required param, etc.) do return real 400s with the same `{code, message, moreInfo}` shape, so status-code-based error normalization alone misses this case — the SBDB tool has to separately check for a missing `object` key on an otherwise-200 response.
- **Sentry has three distinct "no current risk" shapes**, all worth surfacing differently to a user rather than collapsing into one generic message: (1) `{error: "specified object not found", signature}` (HTTP 200) — valid designation, never flagged as a risk at all; (2) `{removed: "<date>", error: "specified object removed", signature}` (HTTP 200) — was flagged, later ruled out; (3) a real HTTP 400 `{code, message: "invalid designation"}` — the `des` param only accepts numeric/provisional designations (`"99942"`, `"2000 SG344"`), not common names (`"Eros"` 400s, `"433"` doesn't). Found all three by probing the live API with `curl` before writing any types — cheaper than guessing the shape from docs and having tools throw on real responses later.
- Sentry's per-object `summary` (from `?des=`) and its list-mode entries (from calling with no `des`, or CAD's row data) are **shaped differently** despite covering overlapping fields — e.g. list mode has a `range` (risk-window years) field that the single-object `summary` doesn't; single-object `summary` has `first_obs`/`last_obs`/`darc` instead. Assuming one endpoint's shape applies to a "similar" one is a real bug source here, not just a hypothetical — caught by testing against live responses rather than trusting the field list from one sample call.

- Mars Rover Photos has no server-side pagination — a single sol/date query can return hundreds of photos in one JSON response. Decided to truncate to the first ~20 and report the total count in the text response, rather than embedding real client-side pagination (a `page` param, cursor, etc.) up front. Reasoning: this is a learning project, and building pagination machinery before knowing whether truncation is actually a problem in practice is premature — easy to revisit later (flagged in Phase 8) if 20 turns out to be too few for real use.
- **Mars Rover Photos' upstream is currently broken** — `api.nasa.gov/mars-photos/api/v1/rovers/.../photos` returns a raw Heroku "No such app" HTML page (not JSON, not a NASA error) for every request, including valid ones. The underlying `mars-photo-api` project was Heroku-hosted and the maintainer archived it after running out of time to keep it working post-Heroku's 2022 free-tier shutdown. Confirmed via direct `curl` (not our code) before building anything, so Phase 3 was swapped to NeoWs instead. Worth re-checking periodically in case NASA points the proxy elsewhere.
- **`DEMO_KEY` is a shared, globally-throttled key** — hit `429 OVER_RATE_LIMIT` on it after a modest number of calls during Phase 2/3 testing (a handful of APOD + NeoWs calls), well under the documented 30/hr personal cap. Because `DEMO_KEY` is the same key every anonymous NASA API user shares, its quota can be exhausted by *other people's* traffic, not just your own — it's unreliable for actual dev iteration. A free personal key from <https://api.nasa.gov/> (instant, email-delivered) gives 1000 req/hr and avoids this entirely; worth doing before Phase 3's happy-path re-test.

- **NASA has a third distinct API family beyond `api.nasa.gov` and JPL's SSD API**: `svs.gsfc.nasa.gov` (Scientific Visualization Studio's "Dial-A-Moon"), also no key needed. Confirmed live via `curl` before building `src/svs-client.ts` — same approach as SSD API verification in Phase 6, worth doing every time before trusting an endpoint's documented shape.
- Dial-A-Moon's datetime path segment (`/api/dialamoon/YYYY-MM-DDThh:mm`) requires the full time — a date-only path (`.../2026-07-23`) 404s rather than defaulting to midnight. Its error responses are also HTML, not JSON (unlike `api.nasa.gov` and the SSD API), so error normalization can't assume a parseable JSON body — `svs-client.ts`'s error path falls back to `res.statusText` rather than trying to extract a message field.
- **JPL Horizons (`ssd.jpl.nasa.gov/api/horizons.api`) is a fourth, distinct API host** — not the same as `ssd-api.jpl.nasa.gov` used for SBDB/CAD/Sentry, despite being the same JPL infrastructure family and sharing the "serialize requests, no documented rate limit but be conservative" posture. Easy to assume it lives at `ssd-api.jpl.nasa.gov/horizons.api` by pattern-matching the other three tools — it 404s there. Confirmed the real host by trial with `curl` before writing any client code.
- **Horizons string-type query params need literal single quotes *inside* the value**, e.g. `COMMAND=` gets the literal string `'299'` (quotes included), not `299` — a Horizons-specific quoting convention baked into their API design, not standard URL encoding. Building the URL with `curl -G --data-urlencode` (which handles the outer URL-encoding) while manually wrapping each value in `'...'` was what got a working request; naively passing `299` unquoted or letting a URL constructor set it directly returns no error but silently misbehaves.
- **Horizons returns a fixed-width text ephemeris table inside a JSON `{result: "..."}` wrapper, not structured JSON** — a real departure from every other tool in this project. Requesting a 1-hour `STEP_SIZE` with a `STOP_TIME` just one minute after `START_TIME` is a trick to get back exactly one data row (a "snapshot" query) instead of a real time series, keeping the parsing simple. The row's leading "flag" column (interfering-body marker) is sometimes blank and sometimes a character, which shifts the token count — parsed by taking the last 4 whitespace-separated tokens (azimuth/elevation/magnitude/surface-brightness) from the end of the line rather than by fixed position, since those 4 are always exactly at the end regardless of the flag column.
- Horizons errors come back as HTTP 200 with an `error` key in the JSON body (confirmed via an intentionally invalid body ID) — same "don't trust `res.ok` alone" lesson as SBDB's not-found case, but a different shape again (top-level `error` string here vs. SBDB's `{code, message}`). Every NASA-family API in this project has turned out to signal "soft" errors differently; check by probing before assuming any one pattern generalizes to the next endpoint.
- Dial-A-Moon's times are UTC with no timezone parameter — `moon-phase.ts`'s `hour` input is documented as UTC rather than pretending to do local-time conversion, since guessing the caller's timezone isn't something the tool can know. Also means the tool's "today" default (`new Date().toISOString().slice(0,10)`) is UTC's today, which can be one calendar day ahead of the caller's local today depending on time of day — a real, observed quirk (not hypothetical) during testing near a UTC day boundary.
- **DONKI's `/DONKI/GST` silently ignores malformed date params instead of erroring** — `startDate=garbage` returns the exact same result as omitting `startDate` entirely (confirmed by comparing result counts). Unlike NeoWs (which does reject bad ranges) or the SSD/Horizons APIs (which return explicit 400s), there's no server-side signal here at all — Zod's regex validation on `start_date`/`end_date` is the *only* thing standing between a typo and a silently-wrong date range.
- **Geomagnetic latitude, not geographic latitude, governs aurora visibility — and the two can differ by 10+ degrees in North America.** Found this the hard way: an early version of `geomagnetic_storms` compared a user's raw latitude against the standard Kp→latitude table and said the well-documented May 10, 2024 G5 storm (widely seen from the US Northeast) "likely isn't visible" from New York City (40.7°N geographic). Root cause: Earth's magnetic pole is offset toward northern Canada, which pulls North American geomagnetic latitudes north of their geographic ones (NYC ≈ 50°N geomagnetic). Fixed with a simple dipole-approximation conversion (`geomagneticLatitude()` in `geomagnetic-storms.ts`) before comparing. General lesson: when a tool's output can be checked against a real, well-known event, do that check — this bug would have shipped clean through schema validation and a happy-path test that only checked "does it return text," since nothing about the *shape* of the response was wrong, only its accuracy.
- APOD's `media_type` can be `"video"` (no `url` pointing at an image) — a tool that always tries to fetch/embed an image needs to branch on this rather than assume every day has a photo.
- `hdurl` is sometimes absent even when `hdurl` would normally be present; fall back to `url` if the caller asked for HD but it's missing.
- **APOD caching (`src/lib/cache.ts`) deliberately has no TTL** — a past date's APOD is immutable once published, so a plain memoization Map is correct and simpler than an expiring cache. The one trap: caching under a literal `"today"` key would keep serving yesterday's picture forever once the date rolls over on a long-lived server process. Fixed by resolving `date` to a concrete `YYYY-MM-DD` (UTC, same "today" convention as `moon-phase.ts`) *before* building the cache key, so each calendar day naturally gets its own cache entry. Verified with a scripted client: same-date second call dropped from ~2000ms to ~5ms.

## MCP SDK / TypeScript gotchas

- `registerTool`'s `inputSchema` takes a **raw shape** (a plain object of Zod schemas, e.g. `{ date: z.string().optional() }`), not a `z.object({...})` — the SDK wraps it internally.
- Thrown errors inside a tool handler are caught automatically by the SDK and turned into a `CallToolResult` with `isError: true` — no need for a try/catch in every handler just to report failure to the client. Same applies to Zod input-validation failures: they never reach the handler as a thrown exception the *caller* sees; the client gets back `isError: true` with the validation message in a text block, not a rejected promise/protocol-level error.
- `tsconfig.json` needs `"types": ["node"]` in `compilerOptions` for Node globals (`process`, `Buffer`) to resolve under `strict` mode, even with `@types/node` installed as a dependency — install alone isn't enough.
- For manual testing without the interactive Inspector UI, spin up an MCP `Client` + `StdioClientTransport` in a small script that spawns `tsx src/index.ts` — lets you call `listTools()`/`callTool()` programmatically and assert on results, which is more scriptable than clicking through Inspector for every check.
- `console.error` (stderr) is safe for debug/warning output from inside a stdio MCP server; `console.log` (stdout) is not — stdout is the JSON-RPC transport channel, and anything non-protocol written there would corrupt the stream from the client's perspective. The SSD client's version-mismatch warning uses `console.error` for this reason.
- A serialization queue (promise chain) needs to advance past *failures*, not just successes, or one bad request permanently jams every subsequent call. `queue = result.then(() => undefined, () => undefined)` — chaining onto both branches of `.then()` — keeps the queue's own promise always resolving regardless of what the task did, while the caller's returned promise (`result`) still carries the real success/rejection. Verified with a test where the first mocked call 400s and a second call afterward still succeeds.
- `registerResource(name, uri, config, readCallback)` confirms the tool/resource split at the protocol level, not just conceptually: resources show up under a separate `resources/list` RPC method (`client.listResources()`), and reading one is `resources/read` (`client.readResource({ uri })`) — entirely different methods from `tools/list`/`tools/call`. The read callback gets the parsed `URL` and returns `{ contents: [{ uri, mimeType, text }] }`, mirroring a tool's `{ content: [...] }` shape but keyed `contents` (plural, no `type` field — mimeType does that job).

- **Error normalization is worth branching on status, not just forwarding NASA's message verbatim.** NASA's own `429` body (`OVER_RATE_LIMIT`) doesn't tell the caller *why* — a shared `DEMO_KEY` failing vs. a personal key failing call for different next steps (get a key vs. wait out the window). `throwNormalized` in `nasa-client.ts` checks `process.env.NASA_API_KEY` presence to pick the right hint, rather than surfacing NASA's generic message and making the user figure out the fix themselves.
- Wrapping the raw `fetch()` call in try/catch (not just checking `res.ok`) matters — a DNS failure or connection refusal makes `fetch` *reject*, not return a non-2xx `Response`. Without the try/catch, that surfaces as a raw `TypeError` with a confusing stack instead of a normalized `NasaApiError`.
- Tested the error-normalization branches by monkey-patching `globalThis.fetch` in a throwaway script rather than trying to actually trigger a 429/403/network failure for real — faster, deterministic, and doesn't burn API quota. Real happy-path testing (actual data) still needs a real call, so did both: mocked-fetch script for the error branches, one real `apod` call after to confirm nothing broke.

- `claude mcp add <name> -- <command> [args...]` registers a stdio server with Claude Code — the `--` matters, it separates `claude mcp add`'s own flags from the actual command being registered (without it, something like `--env-file=...` gets parsed as a flag to `claude mcp add` itself rather than passed through). Local scope (the default) keeps the registration private to this machine/project rather than committing it to `.mcp.json` in the repo — appropriate here since the command embeds an absolute path.
- **A newly-registered MCP server isn't available in the Claude Code session that registered it** — servers are loaded at session startup, so `claude mcp add` mid-session (confirmed connected via `claude mcp get`) still didn't surface its tools to that same running session. Needs a fresh session to actually test with natural-language prompts.

## Debugging notes

- **`.env` isn't loaded automatically — silent fallback to `DEMO_KEY` masqueraded as a real rate-limit problem.** `nasa-client.ts` reads `process.env.NASA_API_KEY` directly, but neither Node nor `tsx` reads `.env` files on their own; nothing in this project used a `dotenv`-style loader. So a real personal key sitting in `.env` was never actually reaching the process — every run silently fell back to the shared `DEMO_KEY`, which is what was producing `429` errors in the Inspector even though a working key already existed. Fixed by adding `--env-file=.env` to the `dev`/`start`/`inspect` npm scripts in `package.json` — Node 20.6+ supports this flag natively (confirmed on Node 24 here), and `tsx` forwards it straight through to Node, so no `dotenv` dependency was needed. Lesson: if a fix "should" work but the symptom persists, check whether the config is actually reaching the process before assuming the fix is wrong.
